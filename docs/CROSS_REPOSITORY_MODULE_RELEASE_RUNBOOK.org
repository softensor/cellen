#+TITLE: Cross-Repository Module Integration and Release Runbook
#+DATE: 2026-08-07
#+STARTUP: overview

* Purpose

Use this runbook whenever Cellen consumes a module or package maintained in a
different repository.  It records the release lessons from the Cellen--Finreg
integration so that backend deployment, Flutter builds, private dependencies,
GitHub Pages, and production activation are handled as separate, explicit
stages.

* Core release model

A cross-repository integration has at least four independently deployable
parts.  Never treat a successful push as proof that all four are live.

| Part | Example | Proof of deployment |
|------+---------+---------------------|
| Provider source | Finreg integration branch | Exact commit exists on GitHub |
| Consumer backend | Cellen API on VPS | VPS commit, migration head, service health |
| Provider backend | Finreg API/worker/Beat on VPS | VPS commit, migration head, readiness |
| Consumer frontend | Cellen Flutter/GitHub Pages | Successful build and Pages deployment from release branch |

Functional activation is a fifth stage.  Code may be deployed while a tenant
remains in =shadow= or behind a kill switch.  Deployment and activation must
not be conflated.

* Preflight before opening a pull request

1. Record the exact provider and consumer commit IDs.
2. Determine whether every referenced repository is public or private from an
   unauthenticated environment.  A developer's credential manager is not
   available to GitHub Actions.
3. Inspect path dependencies in =pubspec.yaml=, package manifests, generated
   clients, Git submodules, and build scripts.  A local sibling path such as
   =../../finreg/packages/...= requires the same directory topology in CI.
4. If a private provider is required, create or reuse a least-privilege token
   with read-only =Contents= access to that provider repository.  Store it as
   a consumer-repository Actions secret; never commit it.
5. Pin the provider checkout to an immutable tested commit, not a moving branch.
6. Verify that workflow path filters include the files changed by the pull
   request and the workflow itself where appropriate.
7. Build locally from a clean checkout that reproduces CI topology.  Do not
   rely only on a workstation where sibling repositories already exist.

* Private dependency pattern

Cellen's Flutter build consumes private Finreg packages.  The supported Actions
secret is:

#+BEGIN_EXAMPLE
FINREG_READ_TOKEN
#+END_EXAMPLE

The value may be an existing authorized PAT; the secret name is only the
workflow's lookup key.  The token must be authorized for =softensor/finreg=
with read-only Contents permission.  Repository-scoped =GITHUB_TOKEN= for
Cellen cannot read a separate private repository.

Use =actions/checkout= with all of the following:

#+BEGIN_SRC yaml
- name: Check out pinned Finreg packages
  uses: actions/checkout@v4
  with:
    repository: softensor/finreg
    ref: ${{ env.FINREG_PACKAGES_REF }}
    token: ${{ secrets.FINREG_READ_TOKEN }}
    path: finreg-source
#+END_SRC

=FINREG_PACKAGES_REF= is one workflow-level immutable full commit SHA shared by
Android, iOS and Web. When a Cellen change consumes a new Finreg SDK or UI
contract, merge and validate Finreg first, update this single pin in the same
Cellen pull request, and verify that every platform resolves that revision.
Never leave one platform on a different or historical package revision.

Expose the directory expected by the consumer's path dependencies only inside
the isolated runner:

#+BEGIN_SRC sh
ln -s "$GITHUB_WORKSPACE/finreg-source" "$GITHUB_WORKSPACE/../finreg"
#+END_SRC

Do not assume that a public-looking browser page means anonymous Git/archive
access works.  A =404= archive response or a username prompt from a noninteractive
=git clone= is evidence that authentication is required.

* Pull-request build versus production deployment

Pull requests must build Android, iOS, and Web but must not deploy GitHub Pages.
The build job must not declare the protected =github-pages= environment.
Instead:

1. Build Web for both pull requests and release-branch pushes.
2. Configure and upload the Pages artifact only outside pull requests.
3. Put =environment: github-pages= on a separate deploy job.
4. Gate that job with =if: github.event_name != 'pull_request'= and make it
   depend on the successful Web build.

The expected PR result is therefore three successful platform builds and one
skipped =Deploy Web= job.  After merge to =master=, =Deploy Web= must run and
succeed.

* Required release sequence

1. Push both provider and consumer integration branches.
2. Open pull requests against the actual release branches.
3. Evaluate checks attached to the latest commit only.  Old failed deployments
   remain visible and are not evidence that the current commit failed.
4. Require backend tests and every applicable frontend build to pass.
5. Merge provider changes before or together with the pinned consumer update.
6. Merge the consumer pull request.
7. Verify the release-branch Flutter workflow and Pages deployment.
8. Hard-refresh or use a private browser window to bypass an old Flutter Web
   service-worker/browser cache.
9. Pull the exact released commits on the VPS.
10. Install dependencies, apply migrations, restart services, and verify local
    and public health/readiness endpoints.
11. Exercise the integration in =fake= or =shadow= mode.
12. Promote tenant mode only after its documented operational, accounting,
    security, and legal gates pass.

** Verify manifest-driven authoritative workspaces

Cellen must not contain a hardcoded catalogue of Finreg ERP modules. The
=/finreg/capabilities= response supplies every configured workspace and its
current operational state. Cellen renders its normal module menu from that
list and retains native screens only for school-specific context. Selecting a
workspace renders Finreg's shared application router and exact page widgets
inside Cellen; it does not copy the page and does not open another application.

Each capability has exactly one entry in the host menu. A vertical may provide
a renderer override for a capability while leaving visibility and entitlement
manifest-driven. For example, Cellen renders its school-aware billing extension
for the canonical =billing= capability; it must not add a second School or Sales
entry beside the generic Finreg billing workspace. Capabilities without a host
override render the authoritative Finreg page unchanged.

Cellen's backend requests and immediately consumes the existing 60-second,
single-use delegated grant to create the embedded user session. Cellen never
receives or stores a Finreg user password, and the browser never receives the
integration client secret. The legacy external launch remains an optional
standalone handoff, not the normal module-menu behaviour.

Embedded routers must override the browser platform location and neglect host
browser history. Cellen's own route must never be interpreted as a Finreg login
route. Sessions are obtained lazily for the selected capability; a failure is
shown as an in-context retry and never as a second login form.

School billing is payer-first. Selecting a guardian resolves only that
guardian's active linked learners. A single learner is assigned automatically;
multiple linked learners are presented as a constrained choice. Cellen must
validate the guardian-learner relationship again on every preview, issuance,
and billing-plan write.

For each release that changes composition or UI manifests, verify all of the
following:

- enabling a capability in the Finreg owner Composition panel makes its
  workspace appear in Cellen after refresh;
- disabling it makes the workspace unavailable and a direct launch request is
  rejected;
- every operational workspace has an entry in Finreg's shared widget registry;
- each capability appears once and =billing= renders the school extension in
  Cellen rather than a duplicate generic Sales entry;
- at least one capability other than Accounting or POS renders its complete
  Finreg page and internal subroutes inside Cellen;
- the normal Cellen module menu does not invoke =url_launcher= or an external
  browser;
- the Cellen browser never receives the integration client secret;
- reusing or waiting more than 60 seconds before exchanging a launch code
  fails;
- the Finreg session has the mapped user's permissions, not platform-owner
  permissions.
- selecting a payer never exposes unrelated learners, and an unlinked
  payer-learner payload is rejected server-side.

Production Cellen configuration must set =FINREG_WEB_URL= to the public Finreg
web origin. =FINREG_BASE_URL= remains the API base ending in =/api/v1=.

* Evidence checklist

Retain these values in the release record:

- Provider commit and consumer commit.
- Pull-request URLs and latest successful workflow run IDs.
- Artifact names and Pages deployment commit.
- VPS checkout branches and commits.
- Database migration heads.
- Service states and health/readiness responses.
- Tenant connection ID, provider company/tenant ID, mode, kill switch, last
  synchronization time, event cursor, mapping errors, and unresolved commands.
- Approval references for pilot and live activation.
- Backup filenames made immediately before fiscal/authoritative cutover.

Never retain passwords, PATs, client secrets, database URLs, private keys, or
AGT credentials in Git, logs, screenshots, or this evidence record.

* Failure signatures and first response

| Symptom | Meaning | First response |
|---------+---------+----------------|
| =Branch refs/pull/... is not allowed to deploy to github-pages= | PR build job entered protected deployment environment | Separate Web build and deploy jobs; skip deploy on PR |
| Path package =doesn't exist= | CI lacks a local sibling repository | Reproduce dependency topology in the runner |
| Private checkout asks for username or returns repository not found | Current token cannot read provider repository | Configure authorized read-only Actions secret |
| Commit archive returns =404= | Provider/ref is not anonymously downloadable | Use authenticated pinned checkout |
| Exit 66 during =flutter create= | Dependency resolution failed; inspect preceding package error | Fix package checkout/path before changing Flutter code |
| Node.js/action deprecation warning | Maintenance notice, not the current build failure | Schedule action upgrades separately |
| PR shows failed outdated deployment | A prior commit/run remains in history | Match check =head_sha= to latest PR commit |
| VPS returns transient =502= after restart | Workers have not completed startup | Wait, then verify local health and journal; investigate only if persistent |

* Finreg school-pilot incident lessons (2026-08-09)

The Rainha Njinga cutover exposed a sequence of individually small assumptions
that together made the release unnecessarily difficult.  Treat the following
as mandatory controls for every future vertical, not as tenant-specific
workarounds.

** Use the complete mode matrix

Operational authority and AGT transport are separate axes:

| Operational mode | AGT channel | Meaning |
|------------------+-------------+---------|
| =shadow= | =disabled= | Compare integration results; never finalize fiscal documents |
| =pilot= | =offline= | Exercise numbering, hashing, signing, accounting, receipts and SAF-T locally; make no AGT network call |
| =pilot= | =sandbox= | Run the same fiscal workflow against AGT homologation credentials |
| =live= | =production= | Approved public fiscal operation |

Deployment scripts and validators must receive or discover both values.  A
validator defaulting to =shadow/disabled= against an intentional
=pilot/offline= tenant produces false failures and is not evidence of a
rollback.

** Make fiscal finalization one atomic persistence boundary

Never allow an ORM query/autoflush between assigning a fiscal number and
persisting the final status, hash-chain fields and signature.  A partial flush
made the database immutability trigger correctly interpret the second update
as an illegal edit of already issued content.  Query prerequisites first, then
assign and flush all protected fields together.  Keep the immutability trigger;
do not weaken it to accommodate application ordering defects.

** Migrate every new persisted vocabulary value

Adding =transmission_disabled= to application logic required widening
=documents.agt_status= from =VARCHAR(20)= to =VARCHAR(30)=.  For every new
status, mode, channel or error code, check all ORM declarations, migrations,
database constraints, API schemas, filters, reports and test fixtures.  CI must
assert that the longest supported value fits the deployed column.

** Treat existing partial state as a recovery workflow

After a failed multi-step attempt, inspect the authoritative row before
retrying.  The August invoice was safely finalized and posted but retained
=agt_status=pending= because the subsequent offline-status update had failed.
Re-running the idempotent transport task reconciled it to
=transmission_disabled= without contacting AGT.  Do not renumber, delete or
manually rewrite an issued fiscal document.

** Exercise background workers, not only HTTP endpoints

Acceptance must invoke the real recurring-invoice Celery task.  This revealed:

- async database resources attached to a different event loop;
- incomplete SQLAlchemy mapper registration in the worker process;
- a required recurring-plan field omitted by the integration endpoint;
- finalization/autoflush behavior that request-level tests had not exposed.

Worker acceptance must prove task receipt, successful completion, idempotency,
document creation/finalization, and absence of new worker errors.

** Preserve deployment ownership and wait for readiness

Run Git inspection as the deployment account even when the acceptance wrapper
runs under =sudo=.  Root-owned =.git/index= and =__pycache__= files can prevent
later pulls and diagnostics.  Avoid bytecode writes during read-only syntax
checks when production caches are not writable.

A process being =active= is not the same as the API being ready.  Finreg needed
more than five seconds on this VPS.  Promotion must wait for readiness with a
bounded retry/poll and must roll back only after that readiness budget expires.

** Use one aggregate acceptance report

Do not ask an operator to test endpoints one by one.  The version-controlled
=deploy/validate_cellen_finreg_release.sh= suite is the release authority.  It
must check repositories, migrations, services, databases, tenant/profile
fingerprints, scopes, secret permissions, mode/channel, mappings, outbox,
recurring generation, idempotency, fiscal state, accounting state, offline
transport isolation, authoritative SAF-T and new service errors.

The fingerprint check must resolve the deployed tenant's authoritative
=vertical_profile=, =enabled_capabilities= and country pack.  A hard-coded
school baseline becomes invalid as soon as the owner changes that tenant's
composition, even when both the stored manifest and runtime behavior are
correct.

The accepted Rainha Njinga pilot/offline baseline was:

#+BEGIN_EXAMPLE
Finreg revision: 9b882fc
Finreg migration head: d4a6b9c1e5f7
Document: OFFFT/2026/1
Document status: finalized
Accounting status: posted
AGT status: transmission_disabled
AGT transmitted: false
Acceptance: 53 passed, 0 failed
Evidence: /home/jorgehel/backups/cellen-finreg-acceptance-20260809-152632.org
#+END_EXAMPLE

This proves the deployed local fiscal pilot behavior.  It is not a statement
of AGT certification or authorization for production transport.

** Keep terminal instructions paste-safe

Operator command blocks must contain commands only.  Prose such as =If this
passes= or =Then= was repeatedly interpreted by the shell.  Prefer short,
restartable blocks; inspect an existing branch before recreating it; use
=set -Eeuo pipefail=; and verify =git diff --check=, syntax, migration heads and
the current branch before committing.  GitHub pull requests, checks and merges
should use the terminal workflow recorded in
=docs/GITHUB_TERMINAL_RELEASE_RUNBOOK.org=.

* Operational invariants

- Never invent legal identities, NIFs, certificates, fiscal series, or approval
  references.
- Never expose a private-repository PAT in workflow YAML or logs.
- Never issue a new fiscal retry key for an unknown outcome.
- Never merge merely because Git reports no conflicts; current required checks
  must pass.
- Never promote all tenants to a new module at once.  Start with one named
  tenant, retain a kill switch, reconcile, then expand deliberately.
- Preserve unrelated untracked media and operator files on production servers
  and developer workstations.

* Maintenance after a successful release

Update deprecated Actions in a dedicated change so release failures remain
easy to diagnose.  Rotate read-only repository tokens before expiry and update
the consumer secret without changing workflow code.  When the provider commit
is upgraded, change the pinned ref, run the complete matrix, and record the new
provider/consumer pair.
